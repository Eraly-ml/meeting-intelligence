# MeetingBox hub — optional native-client prototype

This is the earlier hub for the `macos/` Swift client. It is retained for development and is **not deployed** on the current Radxa meeting station. The active architecture uses [`station/`](../station/README.md) on the board and [`mac-worker/`](../mac-worker/README.md) on the Mac; see [the runbook](../docs/RUNBOOK.md). The setup below belongs only to this prototype and should not be started alongside the station as its replacement.

The hub receives timestamped text from Macs and runs one local Ollama reasoning job at a time. It never downloads models, calls commercial APIs, or sends audio/text to an Internet endpoint. Install dependencies and model weights before an offline demo. Live capture and recording imports are handled by the native Mac client.

From the repository root:

The prototype's file-based configuration is `backend/.env`, copied from `backend/.env.example`. `scripts/run-hub.sh` loads that file (or an explicit `MEETINGBOX_ENV` path). The root `.env.example` belongs to the deployed Mac worker. The following equivalent setup passes settings through environment variables:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -e 'backend[test]'
export MEETINGBOX_TOKEN="replace-with-a-long-random-shared-token"
export MEETINGBOX_DATABASE="$PWD/data/meetingbox.sqlite3"
export MEETINGBOX_MODEL="qwen2.5:3b"
.venv/bin/python -m uvicorn meetingbox.main:create_app --factory --host 0.0.0.0 --port 8000 --workers 1
```

Run the preinstalled Ollama service on the same appliance with `OLLAMA_HOST=127.0.0.1:11434` and `OLLAMA_NO_CLOUD=1`. For a manually launched service:

```sh
OLLAMA_NO_CLOUD=1 OLLAMA_HOST=127.0.0.1:11434 ollama serve
```

The default model name is a starting configuration, not a performance guarantee for the Cubie hardware. Use a model you have already downloaded or imported, measure latency and memory on the board, and configure `MEETINGBOX_MODEL` accordingly. The hub refuses model names containing `cloud`, HTTP redirects, nonloopback model addresses, and `/api/show` metadata indicating a remote model or lacking local GGUF weights. Its HTTP client disables environment proxies. Disabling cloud in Ollama itself prevents changes elsewhere in Ollama from enabling cloud inference. The application has no third party scripts, hosted docs UI, analytics, tool calls, or autonomous web access.

Use the same Bearer token in the Mac app. All HTTP endpoints, including health and exports, require it. The demo token grants access to all office meetings: this MVP has no per-person authorization. HTTP on a trusted LAN provides authentication but no transport encryption; for sensitive deployments put the hub behind locally managed TLS and configure the Mac for `https`/`wss`. The database and recordings are ordinary local files; storage encryption and retention are deployment responsibilities.

## API contract

All IDs are UUIDs generated by the client, so an offline Mac can create a meeting before the hub reconnects. Every request uses `Authorization: Bearer <token>`.

| Request | Behavior |
| --- | --- |
| `GET /health` | Hub process health and configured model; does not claim model readiness. |
| `POST /meetings/start` | Body `{meeting_id,title}`. Same ID/title is replayable, conflicting title is HTTP 409. Returns a meeting snapshot. |
| `POST /meetings/{id}/segments` | Body `{segments:[{sequence,start,end,speaker,text}]}`. Returns `{ack_sequence}` for the highest **contiguous** committed sequence. |
| `POST /meetings/{id}/end` | Body `{last_sequence}`. Requires every sequence 1…N and rejects any later buffered sequence. Durably queues the final report; same end is replayable. |
| `GET /meetings/{id}` | Full durable snapshot, including segments and report. |
| `GET /meetings?limit=100&offset=0` | `{meetings:[...]}` with newest meetings first. |
| `GET /search?q=report` | `{results:[...]}` with literal transcript keyword matches and source sequence/timestamps. This is keyword search, not vector RAG. |
| `GET /meetings/{id}/export?format=markdown` | Download report and complete transcript; `format=json` returns a full machine readable snapshot. |
| `POST /meetings/{id}/retry` | No body. Requeues a failed final report after fixing local model configuration. |
| `WS /ws/{id}` | Bearer **header**, never a token in the URL. Sends `{type:"snapshot",meeting:{...}}` immediately and after changes. Reconnect fetches current committed state. |

Segments use integer `sequence >= 1`, seconds from a common recording clock, `end >= start >= 0`, and speaker `local`, `remote`, or `unknown`. These labels identify audio channels, not people. A batch accepts 1–128 segments; text is limited to 8,000 characters per segment and request bodies to 2 MiB. Identical segment replays succeed even after ending; conflicting content or new segments after ending return HTTP 409. A conflicting batch rolls back completely. Sequence gaps are stored but never acknowledged past the gap. The client should retain its full transcript, resend unacknowledged sequences, and submit `/end` only after the hub acknowledges all of them.

Snapshots contain:

```json
{
  "meeting_id": "<uuid>",
  "title": "Planning",
  "status": "recording",
  "last_sequence": 0,
  "final_sequence": null,
  "report_sequence": 0,
  "created_at": 0.0,
  "updated_at": 0.0,
  "segments": [],
  "report": null,
  "error": null
}
```

Statuses are `recording`, `processing`, `complete`, and `failed`. Timestamps `created_at` and `updated_at` are Unix seconds. Reports use `summary`, `decisions:[{text,evidence:[sequence]}]`, `action_items:[{task,owner,due,evidence:[sequence]}]`, `open_questions:[string]`, `topics:[string]`, and `risks:[string]`. Unknown owner and due are JSON null. Evidence validation proves referenced segments were supplied; it does not prove a model's interpretation is correct. Reports should be reviewed before acting on assignments.

## Durability and scheduling

SQLite uses WAL, `synchronous=FULL`, and explicit transactions. An acknowledgement is sent after its commit. Finalization and its job are one transaction. A process lock prevents two hub instances from opening the same database, and deployment must use exactly one Uvicorn worker. Back up the database through SQLite's backup API or stop the service before copying database/WAL files.

Every approximately 45 seconds, each changed live meeting gets a coalesced incremental job. Final jobs have priority. Exactly one worker invokes Qwen, while the HTTP service continues accepting other meetings. An unavailable model retries with persisted backoff, then exposes an error and `failed` status for final processing. It never manufactures a report as a fallback. A crash leaves running jobs durable; restart requeues them. Obsolete incremental jobs cannot overwrite a final report after recovery.

Incremental processing carries the last report forward. Final processing revisits the entire transcript sorted by speech timestamps, because separate transcribers can deliver older speech later. Long meetings use chronological progressive reconciliation under a conservative UTF-8 byte/context budget; oversized segments are split without dropping characters and retain original sequence references. No transcript prefix is silently discarded. If the accumulated report itself cannot fit, processing fails explicitly; increase `MEETINGBOX_CONTEXT_TOKENS` on hardware that can support it. Progressive summarization can still lose semantic detail, so raw transcript and evidence remain available for review.

WebSocket notification queues hold one refresh token per listener, so bursts coalesce into the latest durable snapshot. A send blocked for ten seconds disconnects the slow client. Snapshots include the complete transcript; very long histories will eventually benefit from paginated transcript retrieval and smaller delta events.

Configuration includes `MEETINGBOX_INCREMENTAL_SECONDS` (45), `MEETINGBOX_MODEL_TIMEOUT` (180), `MEETINGBOX_CONTEXT_TOKENS` (8192), `OLLAMA_URL` (`http://127.0.0.1:11434`), database path, model, and token. More than three consecutive attempts requires explicit final retry; incremental updates try again on the next scheduled cycle.

## Validation

```sh
.venv/bin/python -m pytest backend/tests -q
```

Tests use an explicit in-process model double and HTTP mock transport. They exercise authentication, transcript gap/replay rules, transactions, immutable finalization, recovery, failed jobs, chronology, evidence/schema rejection, WebSocket reconnects, network restrictions, and full Unicode transcript coverage across model batches. They do not measure actual Whisper/Qwen quality, board throughput, or live network failures.
